>>¿Qué distingue al plan de gestión de datos de los demás documentos del proyecto?<<
( ) Que es el único que exige el financiador
(x) Que su asunto central es qué ocurre con los datos una vez terminado el proyecto
( ) Que es el único que se puede modificar una vez presentado
( ) Que sustituye al protocolo en lo relativo a los datos
[explanation]
No es el único documento que mira más allá del cierre —el protocolo de un ensayo fija durante cuántos años se archiva su expediente, y la hoja de información dice qué se podrá hacer con los datos más adelante—, pero en aquellos eso es un apartado entre muchos y aquí es **el asunto**.

El protocolo se agota cuando termina la recogida; la memoria, cuando se justifica la ayuda; el artículo, cuando se publica. El plan dice qué ocurre con los datos **cinco, diez o veinticinco años después del cierre**, cuando probablemente no quede nadie del equipo original.
[explanation]

>>Un proyecto no es competitivo: lo financia el propio centro con fondos internos. ¿Hace falta un plan de gestión de datos?<<
( ) No: el plan solo es obligatorio en convocatorias competitivas
(x) Puede seguir siendo obligatorio, porque muchas instituciones lo exigen por su propia política de datos
( ) No, salvo que los resultados se publiquen en una revista que lo pida
( ) Sí, y en ese caso con la plantilla de la Comisión Europea
[explanation]
De ahí que la pregunta útil no sea «¿me exigen un plan?», sino **«¿quién me lo exige, con qué plantilla y para cuándo?»**. La exigencia puede venir del financiador, de la institución o de los dos a la vez, y cada uno pone su propia plantilla y su propio plazo.

Y hay algo que no depende de ninguno de los dos: un proyecto sin obligación de presentar plan tiene exactamente los mismos datos, las mismas obligaciones legales y el mismo problema dentro de diez años.
[explanation]

>>¿Cuándo debe escribirse la primera versión del plan?<<
( ) En los seis primeros meses del proyecto, una vez concedido
( ) Cuando el comité de ética lo solicite
(x) Al preparar la solicitud, antes de recoger el primer dato
( ) Al cerrar el proyecto, documentando lo que se hizo
[explanation]
Porque muchas decisiones **caducan**: qué autoriza el consentimiento, cómo se codifican los sujetos, en qué formato se recoge cada variable, y sobre todo **qué presupuesto tiene la gestión de datos**. Si no se consigna en la memoria económica, después no hay con qué pagarla.
[explanation]

>>Según la prueba que propone esta unidad didáctica, ¿cómo se distingue un plan escrito como guía de uno escrito como trámite?<<
( ) Por su extensión
( ) Por si usa la plantilla del financiador
(x) Por si al escribirlo hubo que preguntar cosas que no se sabían
( ) Por si lo ha revisado un servicio de apoyo
[explanation]
Un plan escrito de verdad obliga a preguntar: si esa carpeta tiene copias de seguridad, cuánto hay que conservar, si el consentimiento permite reutilizar, dónde residirá la imagen. **Si no hubo que preguntar nada, no se decidió nada.** La extensión no distingue: un plan de veinte páginas puede no decir nada del proyecto.
[explanation]

>>En un plan de gestión de datos, ¿cuál es la unidad sobre la que se repite la descripción?<<
( ) El proyecto
(x) Cada conjunto de datos
( ) Cada sistema de almacenamiento
( ) Cada apartado de la plantilla
[explanation]
Los bloques centrales de cualquier plantilla —qué contiene, dónde vive y en qué condiciones, cómo está documentado, cómo se protege— **se repiten tantas veces como conjuntos de datos tenga el proyecto**. Así está construido el modelo común de la RDA, y así están construidas en el fondo todas las plantillas.

El proyecto aparece una sola vez, en la cabecera: título, financiador, quién responde. Y es la razón de que toda la unidad didáctica D2 se dedicara a saber cuántos conjuntos hay.
[explanation]

>>A mitad de proyecto se decide ampliar la extracción de historia clínica a un periodo anterior al previsto. ¿Basta con actualizar el plan?<<
( ) Sí: el plan se versiona precisamente para eso
(x) No: hay que obtener antes la autorización que corresponda, y el plan se actualiza después
( ) Sí, siempre que quede anotado en el historial de cambios
( ) No, y además obliga a rehacer el documento desde cero
[explanation]
Actualizar el plan **documenta** un cambio; no lo autoriza. Ampliar la población o el periodo de una extracción cambia lo que el comité autorizó, de modo que es una **modificación** con su propio trámite, y puede arrastrar además presupuesto, acuerdos y consentimiento.

La pregunta que separa un cambio menor de uno mayor es siempre la misma: ¿afecta a lo que se le dijo al paciente, a lo que autorizó el comité o a lo que se comprometió con el financiador? Cambiar la codificación de una variable o renombrar un fichero, no; esto, sí.
[explanation]

>>¿Cuál es el defecto dominante en los planes de gestión de datos que se presentan?<<
( ) Errores en la normativa citada
( ) Falta de apartados obligatorios
(x) Apartados completos con frases genéricas que no comprometen a nada
( ) Exceso de detalle técnico
[explanation]
Es el fallo más frecuente y el más invisible: el documento **parece completo** —todos los apartados cumplimentados, redacción correcta— pero está lleno de frases que valdrían para cualquier otro proyecto y que no permiten comprobar nada. Los errores de contenido son mucho menos comunes.
[explanation]

>>El plan declara que al terminar el proyecto la base de datos se depositará en un repositorio de acceso controlado. La hoja de información y consentimiento que firman los pacientes no dice nada sobre ceder los datos a terceros. ¿Qué ocurre aquí?<<
( ) Nada, mientras el acceso al repositorio sea controlado y no abierto
(x) El plan promete algo que el consentimiento no ampara: dos documentos del proyecto se contradicen
( ) Que falta indicar en el plan el nombre concreto del repositorio
( ) Que el plan debería citar expresamente la normativa de protección de datos
[explanation]
Es una **incoherencia entre documentos del mismo proyecto**, y es el tipo de problema que un comité detecta y que detiene la tramitación a la espera de aclaraciones. No es un error de fondo ni de redacción: es que el plan y el consentimiento describen cosas distintas.

Que el acceso sea controlado no lo resuelve. Ceder los datos a un tercero, aunque medie una autorización y un acuerdo de uso, sigue siendo una finalidad que el consentimiento tiene que contemplar.

Y tiene dos momentos con costes muy distintos. **Antes de presentar**, se arregla leyendo seguidos el plan, el protocolo y el consentimiento, y corrigiendo el que toque. **Después**, cuando ya hay pacientes reclutados, el consentimiento no se puede rehacer, y lo que hay que corregir es la promesa del plan.
[explanation]
