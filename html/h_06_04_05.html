>>¿Qué se espera del investigador en el apartado legal del plan de gestión de datos?<<
( ) Que determine por su cuenta la base legal de cada tratamiento
(x) Que declare la base determinada y describa los tratamientos con precisión suficiente
( ) Que reproduzca los artículos aplicables del RGPD
( ) Que adjunte el informe del delegado de protección de datos
[explanation]
La base legal se determina con el delegado de protección de datos y el comité de ética, no en solitario.

Lo que sí depende del investigador es **describir con precisión qué tratamientos hay**: sin esa descripción nadie puede determinar nada.
[explanation]

>>Un plan declara únicamente la base del artículo 6 del RGPD para unos datos de salud. ¿Está completo?<<
( ) Sí, el artículo 6 cubre todos los tratamientos
(x) No: los datos de categoría especial necesitan además una excepción del artículo 9
( ) No, falta citar la LOPDGDD
( ) Sí, siempre que haya dictamen ético favorable
[explanation]
Los datos de salud son **categoría especial** y su tratamiento está prohibido con carácter general salvo que concurra una de las excepciones del artículo 9. Hacen falta las dos habilitaciones a la vez.
[explanation]

>>El consentimiento del estudio no menciona el depósito en repositorio, y el apartado 9 del plan promete depositar el conjunto en acceso controlado. ¿Qué pasa?<<
( ) Nada: el acceso controlado no requiere mención en el consentimiento
(x) Hay una contradicción interna que el comité detectará
( ) Basta con seudonimizar antes de depositar
( ) Se resuelve pidiendo autorización al financiador
[explanation]
Es una contradicción entre documentos, y el comité lee los dos.

Lo correcto es declarar el límite en el apartado 6 y ajustar el 9 en consecuencia: por ejemplo, depositar solo datos agregados. Un plan que **declara un límite** es correcto; uno que lo oculta acaba fallando más tarde.
[explanation]

>>Unos datos están seudonimizados y la tabla de correspondencia la custodia el servicio de informática, sin acceso del equipo investigador. ¿Están anonimizados?<<
( ) Sí, porque el equipo no puede reidentificar
(x) No: mientras exista la clave en algún sitio, siguen siendo datos personales
( ) Depende de si la clave está cifrada
( ) Sí, a efectos del depósito en repositorio
[explanation]
No. La existencia de la clave, esté donde esté, mantiene los datos dentro del ámbito del RGPD.

Separar la custodia **reduce el riesgo** y es una buena medida, pero no cambia la naturaleza del dato. Confundir las dos cosas es el error más repetido de este apartado, y lleva a prometer depósitos en abierto que no se pueden cumplir.
[explanation]

>>Un proyecto envía la base de datos a un bioinformático de otra institución para el análisis. ¿Qué es eso?<<
( ) Un uso interno del equipo investigador
(x) Una salida de datos que debe declararse, con su instrumento jurídico
( ) Una transferencia internacional
( ) Una cesión que no requiere formalización si se seudonimizan los datos
[explanation]
Es una salida de datos hacia alguien ajeno a la institución, y debe declararse: qué conjunto, en qué nivel de identificabilidad, para qué y con qué instrumento.

Es además el flujo que peor se documenta en la práctica: la base viaja por correo electrónico sin que ningún documento del proyecto lo mencione.
[explanation]

>>¿Por qué un servicio en la nube puede constituir una transferencia internacional sin que nadie lo perciba?<<
( ) Porque los proveedores no informan de dónde alojan los datos
(x) Porque los datos salen del EEE sin que nadie tenga la sensación de estar enviándolos a ninguna parte
( ) Porque el RGPD no se aplica a los servicios en línea
( ) Porque el cifrado en tránsito exime de declararla
[explanation]
Una herramienta de análisis en línea, una plataforma de encuestas o un servicio de transcripción sacan los datos igual que un envío explícito, pero **no se parecen a un envío**.

Es una de las razones por las que el apartado de almacenamiento pide declarar expresamente qué servicios no se usarán.
[explanation]

>>¿Es válido escribir «no procede evaluación de impacto» sin más?<<
( ) Sí, si lo ha dicho el delegado de protección de datos
(x) No: hay que dar el motivo, que es lo que permite comprobar la respuesta
( ) No, porque con datos de salud siempre procede
( ) Sí, si el proyecto es de un solo centro
[explanation]
Un «no procede» sin motivo no es una respuesta comprobable. «No procede porque el proyecto trata datos agregados sin posibilidad de reidentificación» sí lo es.

Es el criterio de suficiencia aplicado a un campo de una sola línea.
[explanation]
